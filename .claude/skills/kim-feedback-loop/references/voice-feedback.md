# 교수님 음성 피드백 처리

녹음 파일을 받은 순간부터 피드백 문서와 체크리스트를 만드는 단계까지 다룬다. 체크리스트를 원고에 반영하는 일은 versioning.md 와 프로젝트 규칙을 따른다.

## 1. 전사 도구

`${KIT}/scripts/transcribe_meeting.py` 는 원천 프로젝트의 두 스크립트를 일반화한 것이다. 65분 녹음을 8청크 병렬로 처리한 방식과, 5.8분 녹음을 단일 스트림으로 처리한 방식을 옵션 하나로 합쳤다.

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--tag` | 파일명 | 출력 파일과 작업 폴더 이름 |
| `--out-dir` | 현재 폴더 | 최종 전사 파일을 저장할 폴더 |
| `--work-dir` | `<out-dir>/_work/<tag>` | 청크 WAV 와 체크포인트 폴더. 전사 결과가 아니므로 `.gitignore` 에 넣는다 |
| `--language` | `ko` | 전사 언어 코드 |
| `--model` | `small` (또는 환경변수 `WHISPER_MODEL`) | faster-whisper 모델 이름 |
| `--chunk-sec` | 480 | 청크 목표 길이(초). 약 8분 |
| `--chunks` | 자동 | 청크 수를 직접 지정 (지정 시 `--chunk-sec` 무시) |
| `--workers` | `min(청크 수, 8)` | 병렬 프로세스 수. CPU 스레드를 프로세스 수로 나눠 배분 |
| `--terms` | 없음 | 전문 용어를 쉼표로 나열. 초기 프롬프트로 전달 |
| `--ffmpeg` | `ffmpeg` | ffmpeg 실행 파일 경로 |
| `--plan-only` | 꺼짐 | 청크 계획만 출력하고 종료 |

동작 순서:
1. ffmpeg 로 16 kHz 모노 WAV 를 만든다. 최신 파일이면 재사용한다.
2. 앞뒤 12초가 겹치도록 청크 WAV 를 자른다.
3. 청크마다 JSON 체크포인트를 저장한다. 임시 파일에 쓴 뒤 교체하므로 중단돼도 반쪽 파일이 남지 않는다.
4. 체크포인트를 시간순으로 합치고, 겹침 구간에서 중복된 문장을 제거한다.
5. `<작업명>_<모델>.txt` 와 `_segments.json` 을 저장한다. 이름이 있으면 `_v2` 를 붙인다.

원천에서 얻은 교훈 (16코어 CPU 기준):
- 65분 녹음을 단일 스트림 medium 으로 처리하면 예상 소요가 약 5.3시간이었다. 실용이 안 되어 청크 병렬 + small 로 바꿨다.
- 병렬 실행 중 세션이 끊겨 결과가 모두 사라졌다. 그래서 청크마다 체크포인트를 남긴다.
- 청크 WAV 를 지우지 않으면 다른 모델로 다시 돌릴 때 분할 시간이 들지 않는다.
- 체크포인트는 모델 이름별 폴더에 나눠 저장한다. 다른 모델로 다시 돌려도 기존 결과가 덮이지 않는다 (원천 프로젝트 전사 스크립트의 설계를 옮겼다).

필요 조건: `pip install faster-whisper`, ffmpeg. 전사는 CPU 에서 돈다.

참고: 예전 프로젝트 문서에는 openai-whisper base 모델이 적혀 있었지만, 실제 작업은 faster-whisper small 로 했다. 프로젝트 `CLAUDE.md` 의 도구 설명을 실제에 맞게 고친다.

## 2. 전사 품질과 해석 규칙

- 인식 품질은 기대보다 낮을 수 있다. 원천에서도 전사 품질이 낮다고 기록했다. 고유명사, 영문 용어, 전공 용어는 `--terms` 로 미리 알려 준다.
- 전사문은 의미 단위로 정리하되 발언 시각은 그대로 둔다.
- 불분명한 발언은 원문을 옮기고 `(해석)` 을 붙인다. 해석을 사실처럼 쓰지 않는다.
- 교수님이 구술한 답변 문장은 원고에 들어갈 문장의 취지로 기록한다. 원천에서는 교수님이 답변 문장을 직접 말씀하셨고, 원고에도 같은 취지를 넣도록 지시가 있었다.
- 재확인과 새 요구를 구분한다. 이미 반영된 항목에 대한 "됐다", "괜찮다" 는 완료 체크로 기록한다. 새 요구는 체크리스트에 올린다.
- "간단히 하자" 같은 발언은 분량을 줄이라는 지시로 기록한다.
- 교수님의 판단 기준(잣대)을 프로젝트 메모에 따로 적는다. 원천 예: 수치의 크기보다, 자동화가 주는 편익과 프레임워크 논리가 그림으로 쉽게 읽히는지를 보셨다. 이 잣대는 우선순위 판단에 쓴다.

## 3. 결정 사항과 미결 사항

- 결정 사항: 교수님이 명시적으로 정한 것. 날짜와 시각을 적는다.
- 미결 사항: 교수님이 판단을 보류한 것. 임의로 굳히지 않고 "교수님 판단 필요"로 남긴다. 원천 예: 그림 속 한자를 뺄지 말지 결론이 없었던 경우.
- 결정 로그: 교수님 결정은 프로젝트 메모에 날짜와 함께 남긴다. 번복되면 이전 줄을 지우지 말고 새 줄을 추가한다. 원천에서 "원 제출 제목 유지"가 중간에 바뀌었다가 교수님 발언으로 되돌아온 적이 있다. 되돌린 결정에는 "다시 바꾸지 말 것"을 적어 재작업을 막는다.

## 4. 피드백 문서 템플릿

파일명: `feedback_YYYYMMDD.md` (같은 날 파일이 있으면 `_v2`).

```markdown
# 교수님 피드백 — YYYY-MM-DD

- 녹음: <파일명>, <길이> 분
- 전사: <작업명>_<모델>.txt (전문은 전사 파일에 있음)
- 전사 품질: 높음 / 보통 / 낮음. (해석) 표시 <N>곳

## 1. 결정 사항
| # | 대상 | 교수님 말씀 요지 | 시각 | 반영 |
|---|---|---|---|---|
| 1 | 제목 | 원 제출 제목 유지 | [02:11] | v21 본문 제목 복원 |

## 2. 미결 사항 (교수님 판단 필요)
- [09:42] 그림 속 한자 유지 여부. 결론 없음

## 3. 체크리스트
- ☐ [P1] 서론 3문단: 적용 범위 한정 문장 추가. 완료: 초록·서론·결론에 같은 범위 표현 [13:38]
- ☐ [P2] 사례 시나리오 1개 추가. 완료: 표 3에 행 추가, 본문 기술 [16:05]
- ☐ [P3] 그림 7 캡션을 제목만으로 줄임. 완료: 설명 문장은 본문으로 이동 [06:27]
```

원천 `feedback` 명령의 옛 형식(원문 전문 + 체크리스트)을 써도 된다. 그때는 전문을 부록으로 뒤에 붙인다. 검토 속도를 위해 기본은 요약 표와 체크리스트로 쓴다.

## 5. 체크리스트와 우선순위

| 등급 | 대상 | 예 |
|---|---|---|
| P1 | 논문 구조, 주장 범위, 실험 설계 | 장 구조 재배치, 제목·기여 한정 |
| P2 | 사례·시나리오 다양성, 근거 | 사례 추가, 확률·수치의 근거 보강 |
| P3 | 그림과 표 | 그림 통합, 캡션 양식, 가독성 |
| P4 | 문체, 용어, 표기 | 번역체 수정, 약어 통일 |

프로젝트 `CLAUDE.md` 에 우선순위가 있으면 그것을 따른다. 원천 기본값은 3장 구조 > 시나리오 다양성 > 확률 근거 > 그림 > 스타일이다.

항목에는 완료 기준을 쓴다. 완료 기준이 없으면 끝났는지 판정할 수 없다. 예: "3.4절 확률 근거 보강 (완료: 전이확률 출처 명시, 계산 식 1개 추가)".

## 6. 흔한 함정

- 전사 파일을 그대로 피드백 문서에 붙이면 검토가 느려진다. 요약 표로 옮기고 전문은 따로 둔다.
- 시각 인용 없이 요지만 쓰면 나중에 원 발언을 확인할 수 없다.
- 교수님이 언급한 숫자를 목표값으로 바로 쓰지 않는다. 그 숫자의 산출 근거를 확인한다 (numeric-authority.md).
- 최신 녹음 파일이 이번 회의 녹음이 아닐 수 있다. 파일명과 길이를 보고에 적어 확인받는다.
- 여러 녹음이 있으면 날짜별로 피드백 문서를 나눈다. 같은 파일에 합치면 어느 회의 발언인지 흐려진다.
