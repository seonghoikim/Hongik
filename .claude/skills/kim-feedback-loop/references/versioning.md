# 버전 관리 규율

원고, 답변서, 조판본, 전사본을 어떻게 이름 짓고 바꾸고 보존하는지 정한다. 목표는 두 가지다. 교수님이 본 판본과 대조할 수 있을 것, 그리고 언제든 이전 상태로 돌아갈 수 있을 것.

## 1. 파일 이름

- 새 판본: `<이름>_v{NN}.<확장자>`. 번호는 두 자리 0 패딩을 쓴다 (`v07` → `v08`). 원천은 v03 부터 v28 까지 이어졌다.
- 상태를 나타내는 접미사로 중간본을 구분한다. 예: `_draft` (검토 전 초안), `_overlength` (쪽수 초과본).
- 같은 판본의 파생 형식(DOCX 와 PDF)은 같은 번호로 짝을 맞춘다.
- 같은 번호를 두 번 쓰게 되면 타임스탬프(`_YYYYMMDD_HHMM`)를 붙인다. 스크립트 기본 동작은 `_v2`, `_v3` 이다.
- 소스 폴더 번호와 산출물 번호는 다를 수 있다. 원천에서 원고 소스 폴더는 v21 이었고 산출 조판본은 v28 이었다. 조판기는 소스 폴더를 인자로 받는다. 산출물 옆에 "소스: <폴더명>" 을 메모로 남겨 매핑을 잃지 않는다.

### 중간본 삭제 정책
- 기본은 보존이다. 중간본을 지우지 않는다.
- 정리가 필요하면 삭제 대상 목록을 보여 주고 사용자 승인을 받은 뒤 지운다. 원천 메모에서 "지워도 된다"고 적힌 중간본도 사용자가 판단해 표시한 것이다.

## 2. 새 판본 만들기 절차

1. 최신 판본을 찾는다. 파일 목록에서 번호 최댓값을 본다.
2. 다음 번호를 정한다. (`v07` → `v08`)
3. 소스를 새 이름으로 복사한다. 원본은 건드리지 않는다.
4. 패치 스크립트를 파일로 작성해 실행한다. 실행 로그를 남긴다.
5. 산출물을 검사한다 (6절 자가 검사).
6. 체크리스트와 대조해 보고한다.

## 3. 패치는 스크립트로

직접 편집하면 무엇을 바꿨는지 나중에 알 수 없다. 패치 스크립트(예: `apply_v{NN}_{주제}.py`)는 같은 입력에서 같은 출력을 내므로 재현과 롤백이 된다. 원천 파일명 예: `apply_v21_prof.py`, `apply_v16_redraw_author.py`.

- 치환 전에 `assert s.count(old) == 1` 로 대상이 정확히 한 곳에 있는지 확인한다. 0곳이면 조용히 빠진 것이고, 2곳 이상이면 엉뚱한 곳을 고친 것이다.
- heredoc 금지: `python - <<'EOF'` 안의 `\t`, `\f`, `\frac`, `\to` 같은 백슬래시는 파이썬이 해석해 실제 제어문자로 저장한다. 원천에서 수식 한 개가 여러 판본에 물려 내려가며 열흘 넘게 깨진 채 있었다. 패치 파일은 Write 도구로 만들고 실행한다.
- 산출물 검사를 스크립트 끝에 넣는다: `assert not re.search(r"[\t\f\v\b]", text)`. 들여쓰기가 공백인 소스라면 탭이 남아 있는 것은 전부 손상이다.
- 변경 표시 마커(예: `{+ … +}`)를 쓴다면 조판 단계에서만 해석하고, 최종 조판본에 마커가 남지 않았는지 확인한다.

## 4. 조판기(빌더)

- 빌더는 출력 파일명을 인자로 받는다. 예: `build_<문서>.py <출력이름> <소스폴더>`. 기본 파일명을 코드에 박아 두면 기존 판본을 덮어쓰게 된다.
- 시험 조판은 작업 폴더(임시 폴더)에서 한다. 확정한 뒤에만 프로젝트 폴더에 저장한다.
- 쪽수 확인, 쪽별 빈칸 측정 등 조판 점검 스크립트를 따로 둔다.

조판 도구 특성 (필요 조건, Word COM 기준):
- 작업 전 `taskkill /f /im WINWORD.EXE` 로 남은 프로세스를 정리한다. Word 인스턴스는 하나만 쓴다.
- `DisplayAlerts = 0`, `Visible = False`. 저장은 `SaveAs2` 로 새 이름에 한다.
- 표 열 폭을 Word 자동 맞춤에 맡기면 한글 낱말이 한 글자 폭으로 줄어 세로로 쪼개진다. 열의 최소 폭을 가장 긴 낱말 기준으로 먼저 잡고, 남는 폭을 비례 배분한다.
- 찾기·바꾸기의 `Replacement.Text` 는 255자 제한이 있다. 긴 문장은 단락 범위의 `Text` 속성에 직접 쓴다.
- 단락을 삽입한 뒤에는 기존 단락 참조가 어긋난다. 매번 찾기로 다시 얻는다.
- 콘솔 출력이 한글이면 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` 를 넣는다.

## 5. 분량(쪽수) 맞춤

- 상한이 두 개일 수 있다. 저널의 상한과 교수님 기준이다. 더 낮은 쪽을 기준으로 삼는다. 답변서를 쪽수에 넣는지는 사용자에게 확인한다.
- 줄이는 순서 (권장): 중복 서술 → 관련 연구 축약 → 그림 통합(여러 그림을 한 그림의 a–f 패널로) → 표 통합. 원천에서 실제로 쓴 방법은 그림 통합(그림 2개를 2(a)(b)로, 6개를 5(a)–(f)로)과 서술 약 18% 압축이었다. 수치와 그림 자체를 빼는 것은 사용자가 명시적으로 지시했을 때만 한다. 원천 지시는 "그림 합치기는 괜찮지만 빼지는 말라"였다.
- 압축을 에이전트에 맡기면 조건, 단서, 마커를 잘 잃는다. 압축 후 기계 대조(수치 집합, 인용 번호 순서, 표 행과 열 수)를 하고, 어긋난 곳은 원문과 나란히 놓고 수동으로 복원한다 (agent-patterns.md 3절).
- 쪽 하단 빈칸에 주의한다. 그림과 표가 쪽 끝에 들어가지 않아 생긴 빈칸이 압축분을 상쇄하는 일이 많다. 시험 조판으로 쪽별 빈칸을 재고, 그림과 표의 위치를 문단 단위로 옮겨 빈칸을 줄인다.
- 문서 맨 끝의 빈 단락 하나가 한 쪽을 더 만들 수 있다. 쪽수가 한 장 넘으면 먼저 확인한다.
- 작은 표를 한꺼번에 묶으면 빈칸이 생긴다. 쪽 나눔을 허용할 표와 묶을 표를 표시해 구분한다.

## 6. 자가 검사 (산출물마다)

- 제어문자 검사 (3절).
- 변경 마커 잔존 검사: 조판본에 `{+`, `+}` 같은 마커가 없는지.
- 수치 대조: 초록, 본문, 표, 답변서의 같은 수치가 일치하는지 (numeric-authority.md).
- 인용 대조: 본문 인용 번호 집합과 참고문헌 목록 번호가 일치하는지 (references-verification.md 3절).
- 표·그림 번호 대조: 답변서 `@CHANGES` 에 적은 위치가 실제 원고에 있는지.

## 7. Git 과 백업

- 자동 백업 hook 이 있는 저장소에서는 커밋과 push 를 hook 이 맡는다. 수동 push 는 필요 없다. 커밋 메시지는 한글 동사형으로 시작한다: `추가:`, `수정:`, `삭제:`, `개선:`.
- hook 실패는 조용하다. 원천에서는 13일 동안 실패가 쌓여 미커밋 변경이 164건이 된 뒤에야 발견했다. 주기적으로 `git status --short` 의 줄 수를 보고, hook 로그를 확인한다. 로그 위치는 환경마다 다르다. 원천은 임시 폴더의 `claude_hook_backup.log` 에 실패를 남겼다.
- `nul` 사고: bash 에서 cmd 식 `>nul 2>&1` 을 쓰면 실제 파일 `nul` 이 생긴다. Git 은 이 Windows 예약 이름을 인덱싱하지 못해 `git add .` 전체가 fatal 로 끝난다. bash 에서는 `>/dev/null 2>&1` 을 쓴다.
- 이미 `nul` 파일이 생겼다면 일반 삭제는 실패한다. PowerShell 에서 `[System.IO.File]::Delete('\\?\<절대경로>\nul')` 로 지운다. `Test-Path` 는 장치 이름과 헷갈려 False 를 내므로 `[System.IO.File]::Exists('\\?\<절대경로>\nul')` 로 확인한다.
- 전사 스크립트의 기본 작업 폴더 `_work/`, 전사 WAV, 체크포인트, 임시 PDF 같은 중간 산출물은 `.gitignore` 에 넣는다. 커밋 대상이 줄어 백업 hook 이 덜 실패한다.
