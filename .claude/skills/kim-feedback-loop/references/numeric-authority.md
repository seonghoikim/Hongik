# 수치의 권위 출처와 불일치 추적

논문, 발표, 보고서에 쓰는 수치가 어디서 나왔는지 따지는 원칙과, 수치가 맞지 않을 때의 추적 절차를 다룬다.

## 1. 원칙

1. 권위는 재현 가능한 산출 근거에 있다. 입력 데이터 파일, 산출 코드, 실행 결과(시드와 실행 날짜 포함)가 모두 있어야 한다. 문서에 적힌 숫자는 이 근거가 없으면 권위가 아니다.
2. 문서끼리는 서로를 증명하지 못한다. 논문, 발표, 보고서가 같은 숫자를 말한다고 해서 맞는 것은 아니다. 산출 파일과 대조한다.
3. 프로젝트 `CLAUDE.md` 에 "변경 불가"라고 적힌 수치도 근거를 확인한다. 원천에서는 게재된 APFD(결함 검출 순위의 평균 백분율 지표) 0.847 이 "변경 불가" 목록에 있었지만, 산출 근거가 없었다.
4. 서술과 데이터가 충돌하면 데이터 파일까지 내려가 판정한다. 원천 사례: 결함 유형별 개수가 본문 서술(6/5/4/3/2), 설계 문구("균등 배분"), 데이터 파일에서 서로 달랐다. 데이터 파일의 5/4/4/4/3 이 정답이었다. 검증 과정에서 6/5/4/3/2 를 원전으로 믿고 원고를 그 방향으로 고쳤다가, 데이터 파일 기준으로 다시 고쳤다. 데이터 파일까지 내려가지 않았다면 잘못된 방향이 굳어질 뻔했다.

## 2. 불일치 발견 시 추적 절차

### 2.1 재현
같은 입력과 같은 시드로 현재 코드를 다시 실행한다. 값이 다르면 차이를 기록한다. 재현이 안 되는 것인지, 다른 산출 방식의 결과인지 구분한다.

### 2.2 이력 추적
수치가 처음 문서에 나타난 시점과 산출 함수가 도입된 시점을 비교한다.

```
git log -S "0.847" --oneline -- <문서 경로>     # 수치가 처음 나타난 커밋
git log -S "def compute_apfd" --oneline          # 산출 함수가 처음 나타난 커밋
```

원천 결과: 수치는 프로젝트 초기 문서에 이미 있었고, 산출 코드는 한참 뒤에 도입되었다. 수치가 먼저 적히고 구현이 나중에 따라온 것이다. 이 경우 수치는 목표치였고 산출 결과가 아니었다.

### 2.3 과거 산출 재현
해당 커밋의 산출 코드와 데이터를 임시 폴더로 꺼내 실행한다. 저장소 작업 트리는 건드리지 않는다.

```
git show <커밋>:<경로> > <임시 폴더>/<파일>
```

### 2.4 구성 비교 표
의미가 다른 구성을 나란히 놓는다. 예: 결함을 "다중 검출"로 볼지 "단일 검출"로 볼지.

| 구성 | 주 지표 | 무작위 기준 | 검정 p | 효과 크기 | 판정 |
|---|---|---|---|---|---|

### 2.5 의미론 판단
어느 구성이 논문의 설계 주장과 맞는지 판단한다. 원천 사례: 다중 검출 구성은 공통 블록 때문에 아무 순서로나 즉시 검출되는 천장 효과가 생겼다. 통계적으로 구분이 안 되므로 비교 근거로 쓸 수 없다. 단일 검출 구성은 설계(결함마다 전용 검증 시나리오)와 맞고 통계적으로도 구분이 됐다.

### 2.6 옵션 제시
- A: 과거 구성으로 복원. 장단점을 적는다.
- B: 현재 구성을 채택하고 게재 수치를 재산출 값으로 교체. 의미론을 본문에 한 문장으로 명시한다.
- C: 새 의미론을 설계. 비용 대비 이득을 적는다.
- 권고는 하나만 고른다. 근거를 함께 쓴다.

### 2.7 수정 범위 표
교체를 시작하기 전에 수치가 나타나는 모든 위치를 훑는다.

| 위치 | 현재 | 교체 |
|---|---|---|
| 초록, 결론, 기여 문장 | 구 수치 | 재산출 수치 |
| 표와 그림 (파생 값 포함) | 게재 곡선 | 재산출 곡선 |
| 파생 수치 (비율, 절감률) | 구 수치에서 유도 | 재계산 |
| 설정 파일의 기대값 | 구 수치 | 갱신 후 검증 통과 |
| 발표 자료, 보고서 | 인용 | 일괄 갱신 |
| 프로젝트 `CLAUDE.md` 의 불변 수치 | 구 수치 | 산출값으로 갱신 |

### 2.8 정직 공개
투고 전에 발견했다면 "자체 발견 → 원인 확정 → 재계산 → 교체"를 그대로 보고한다. 이 과정 자체가 연구 무결성의 근거가 된다. 재현되지 않는 수치를 그대로 게재하는 것이 가장 큰 위험이다.

### 2.9 검증 장치를 되살린다
기대값과 재계산 값을 비교하는 검증 함수(예: `validate_against_paper`)가 실패 상태로 남아 있었다면, 그것을 작업 차단 신호로 본다. 실패를 무시한 채 다음 작업을 하지 않는다.

## 3. 수치 인용 규칙

- 값은 기준선, 반복 수, 시드, 검정 방법과 함께 쓴다. 예: `APFD = 0.772 vs random 0.500 (N = 10,000, seed 42)`. 숫자는 원천 프로젝트 예시다.
- 소수 자릿수는 산출 파일에 적힌 자릿수를 그대로 쓴다.
- 파생 값(비율, 절감률)은 원 값에서 다시 계산한다. 손으로 옮기지 않는다.
- 문헌 수치를 인용하면 출처와 표 번호를 쓴다.
- 발표 자료의 수치도 같은 규칙을 따른다. 발표 자료가 논문보다 먼저 바뀌면 불일치가 생긴다. 수정 범위 표로 동시에 교체한다.

## 4. 재현 기록 형식

결과 파일마다 다음 정보를 남긴다.

```
결과 파일: <경로>
실행 명령: <명령>
입력: <파일명, 행 수 또는 해시>
시드: <값>, 반복 수: <값>
실행 날짜: YYYY-MM-DD
환경: <가상환경 경로, 주요 패키지 버전>
소스 패치: <외부 코드를 고친 내역. 없으면 "없음">
```

외부 코드를 다른 환경(예: CPU 전용 PC)에서 돌리려면 패치가 필요한 경우가 많다. 원천 사례: 기존 생성 모델을 CPU 에서 돌리려고 GPU 호출을 지우고 옛 타입 별칭을 바꿨다. 이 내역을 기록하지 않으면 재현 결과를 다시 설명할 수 없다.

## 5. 자주 나는 실수

- 발표 자료는 새 수치인데 논문은 옛 수치인 상태로 남는다.
- 보고서의 반올림 자릿수가 논문과 달라 같은 값이 다르게 보인다.
- 두 실험이 서로를 확인하도록 설계되었다면 두 결과 모두에 근거 파일을 명시한다. 한쪽만 근거를 적으면 독립 확인이 아니게 된다.
- 재계산으로 바뀐 값과 옛 값이 같은 표에 섞인다. 원천 사례: 표의 한 행은 원 투고본 기준이고 나머지는 새 기준이었다. 행마다 출처를 밝히거나, 표 전체를 한 기준으로 맞춘다.
- 실험 설정(예: 카탈로그 구성)이 바뀌면 이전 실측 수치를 "구 수치"로 표시해 폐기하고, 본문에서 혼용하지 않는다. 원천 사례: 15단위 실측 값을 12단위 재실행 후 폐기했다.
- 같은 연구에서 파생된 여러 논문은 확정 수치를 공유한다. 한 논문에서 일부 수치를 빼는 것은 가능하지만 값을 바꾸지는 않는다. 값을 바꿔야 할 때는 산출 파일부터 다시 만든다.
