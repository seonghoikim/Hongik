# 저널 심사 대응 (리비전)

수정 후 재심사 판정을 받은 원고의 리비전 계획, 실험 우선순위, 답변서 형식과 문체, 변경 표시, 제출 전 점검을 다룬다.

## 1. 시작 전 확인

- 판정 종류(수정 후 재심사, 조건부 게재 등), 마감일, 제출 형식(변경 표시 방식, 답변서 위치, 쪽수 상한)을 프로젝트 메모에 적는다.
- 마감을 넘기면 재심사가 아니라 신규 투고로 처리될 수 있다. 마감일은 계획 첫머리에 적고 일정의 기준으로 삼는다.
- 저자 목록, 교신 저자, 제출 권한도 확인한다. 제출 시스템의 주소와 계정 정보는 키트 문서에 쓰지 않는다. 제출 작업은 사람이 직접 한다.
- 심사평 원문은 투고 시스템에서 복사해 프로젝트 안에만 둔다. 공유 문서에는 요지로 바꿔 쓴다.

## 2. 지적 분류표 (계획 1단계)

| ID | 심사자 | 요지 | 유형 | 대응 방향 |
|---|---|---|---|---|
| R1-1 | 1 | 주 응용 분야를 정하고 3D 모델이 필요한 이유를 설명할 것 | 서술 | 주 응용 확정, 필요성 문단 추가, 나머지는 향후 연구 |
| R1-4 / R2-4 | 1, 2 | 설계가 보장하는 지표만으로는 부족하다 | 실험 | 정답 기반 벤치마크 (필수) |

규칙:
- ID 는 `R{심사자}-{번호}` 로 쓴다. 같은 취지를 두 심사자가 말하면 `R1-2 / R2-1` 로 묶는다.
- 유형은 다섯 가지 중 하나다: 서술, 실험, 제목·주장 범위, 정보(저자 입력·출처), 교수님 결정 필요.
- 판정 기준:
  - 주장 범위를 좁히면 풀리는 지적 → 서술 (제목, 초록, 결론을 한정)
  - 증거가 있어야 풀리는 지적 → 실험
  - 사실 정보가 없으면 → 저자 입력 요청 (작업 주체, 도구, 소요 시간)
  - 요구가 연구 목적과 맞지 않으면 → 교수님 결정 (3절)
- 긍정 평가(독창성, 학술 가치)는 감사 한 줄로 끝낸다.
- 제목·주장 범위를 바꾸는 조치는 교수님 재승인 대상이다. 승인 전에는 바꾼 제목을 확정하지 않는다. 되돌린 결정은 결정 로그에 "다시 바꾸지 말 것"을 적는다 (voice-feedback.md 3절).

## 3. 연구 목적과 심사 요구가 충돌할 때

원천 사례: 심사자가 정답 데이터로 검증하라고 요구했다. 그런데 논문의 목적은 과거 사람의 행위를 2D 자료에서 예측하는 것이었다. 예측한 행위에는 옳고 그름을 가릴 정답이 없다. 교수님은 이 요구가 목적과 맞지 않는다고 판단하셨다. 행위의 의미는 무엇을 했는지에 있다는 취지다. 대응은 다음과 같이 정했다.

- 답변서 첫머리에 연구 목적을 한 문장으로 명시한다 (예측인지, 재현인지).
- 정답 실험은 "연구 전체의 증명"이 아니라 "각 단계의 기술적 정확도 점검"으로 지위를 낮춰 유지한다.
- 목적과 맞지 않는 지표는 "설계 적합성 점검"으로 재규정한다. 예: 설계가 보장하는 값은 정확도 근거로 쓰지 않는다고 명시한다.
- 이 판단은 답변 문장으로 쓰기 전에 교수님께 확인받는다.

## 4. 실험 우선순위

| 등급 | 기준 | 예 |
|---|---|---|
| 필수 | 심사 핵심 요구에 직접 답함 | 정답 기반 벤치마크, 2D·3D 정확도 |
| 권장 | 지적을 강하게 줄임 | 연쇄 결합 시연, 물리 기반 기준선 |
| 선택 | 효과는 크지만 준비 비용이 큼 | 사용자 연구 |

- 사람이 해야 하는 일은 따로 표시한다. 예: 참가자 모집과 실시는 사람이 한다. AI 가 응답을 만들지 않는다. 기관 연구윤리(IRB) 대상인지 확인한다.
- 정답 기반 실험은 평가 장치부터 검증한다. 정답 값을 그대로 넣었을 때 오차가 0이 나와야 평가 장치가 맞다. 정답은 알려진 관절각으로 리깅 모델을 구동해 렌더하면 골격에서 자동으로 기록된다. 원천도 이 방식을 썼다. 평가 장치를 확인한 뒤에 추정기를 돌린다.
- 실험마다 한 장으로 적는다: 목적, 데이터 구성, 지표, 비교 대상, 산출물, 위험, 소요 시간.
- 실패 결과도 보고 대상으로 미리 정한다. 원천 예: 검출기가 실패하면 그 실패율 자체를 정량 근거로 보고한다.

## 5. 일정 템플릿 (4주)

| 주차 | 작업 |
|---|---|
| 1주 | 결정 사항 확정, 입력 요청, 실험 파이프라인 구축, 서술 수정 초안 |
| 2주 | 실험 실행과 지표 산출, 보강 실험 |
| 3주 | 본문 개정(초록, 서론, 절 단위), 분량 맞춤, 답변서 작성 |
| 4주 | 변경 표시본 조판, 교수님·공저자 검토, 반영, 업로드 |

- 업로드는 마감 2~3일 전을 목표로 한다. 원천 계획은 마감 이틀 전 업로드였다.
- 지연되면 선택 실험부터 뺀다. 지킬 순서는 필수 실험 → 답변서 → 서술 개정 → 선택 실험이다. 선택 실험을 하지 않으면 답변서에 향후 연구로 명시한다.
- 계획 문서는 `<저널약어>_리비전_계획_<날짜>.md` 같은 새 이름으로 만들고, 기준본 버전을 맨 위에 적는다.

## 6. 분량 제약

- 실험을 추가하면 기존 서술을 같은 분량만큼 줄인다. 원천 계획의 원칙이다.
- 상한 초과 시 줄이는 순서는 versioning.md 5절을 따른다.

## 7. 답변서 형식

위치: 수정 원고의 첫 쪽에 조판하거나(편집자 지시가 있을 때), 별도 파일로 둔다.

원천 프로젝트는 답변서 소스를 세 태그로 나눈다. 조판기는 태그마다 다른 스타일을 준다.
- `@COMMENT` 심사평 (요지, 또는 프로젝트 내부에서만 보는 원문. 기울임)
- `@RESPONSE` 답변
- `@CHANGES` 수정 위치 (절, 표, 그림, 참고문헌 번호)

구조 예:
```
Authors' Response to the Reviewers
Manuscript ID: <ID>
Title (unchanged or revised): <제목>

Dear Editor and Reviewers,
We thank ... Section, table, figure, and equation numbers below refer to the revised manuscript.
Main revisions: (5~7개 불릿)

Response to Reviewer 1
@COMMENT 1-1 <요지>
@RESPONSE <답변>
@CHANGES <위치>
```

문체 원칙:
- 지적을 인정하면 "We agree"처럼 짧게 인정하고 조치를 쓴다. 반박은 근거 수치와 함께 짧게 쓴다.
- 감사는 한 문장. 본론을 앞에 둔다.
- 하지 못한 것은 하지 못했다고 쓴다. 예: 사용자 연구를 실시하지 못했으면 향후 연구로 명시한다.
- 원 제출본과 달라진 사실은 밝힌다. 예: 원 투고본의 입력 이미지를 어떻게 준비했는지.
- 모든 번호는 수정본 기준이다. 바뀐 참고문헌 번호는 매핑으로 적는다. 예: `[33][34] → [40][41]`.
- 답변에 쓴 수치는 원고의 표와 문장에 기계로 대조한다.
- 번역체 금지는 한글 문서에 적용한다. 영문 답변서는 영문 간결체로 쓴다.
- 교수님이 "간단히"라고 하면 답변은 감사 한 문장, 조치, 위치로 줄인다.

## 8. 변경 표시

- 프로젝트 정책을 따른다. 원천 정책 예: 변경 부분은 파랑 볼드(또는 변경 내용 추적), 인용은 빨강, 그림·표 참조는 파랑 볼드. 사사(funding) 문구는 원문을 그대로 둔다.
- 소스에는 변경 마커(예: `{+ … +}`)를 두고 조판 단계에서만 스타일을 적용한다.
- 교수님 검토용(변경 표시 유지)과 제출용(표시 정책 확인)을 나눠 만든다.
- 제출 전에 마커가 남아 있지 않은지 검사한다.

## 9. 제출 전 점검

- `@CHANGES` 의 모든 위치(절, 표, 그림, 참고문헌)가 실제 원고에 있는지 스크립트로 대조한다.
- 신규 참고문헌은 DOI 검증을 마쳤고, 번호 재정렬 후 본문 인용과 목록이 일치한다.
- 수치는 초록, 본문, 표, 답변서에서 같다 (numeric-authority.md).
- 쪽수 상한, 저자 정보(약력, 사진, 표기 순서)를 최종 확인한다.
- 유사도(자기표절) 검사를 돌리고 결과를 프로젝트 메모에 남긴다.
- 제출 계정으로 올리는 작업은 사람이 직접 한다.
