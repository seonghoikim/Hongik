# 교수님 심사 잣대, 심사 답변, 검수 (stylechk)

## 1. 교수님이 보시는 것

교수님은 수치의 우수성보다 다음 세 가지를 보신다.
1. 자동화가 주는 편익이 분명한가
2. 자동화를 구축하는 논리 구성과 프레임워크가 있는가
3. 그것이 그림과 도식으로 쉽게 읽히는가

Why: 기준선 대비 수치 비교는 "됐다"는 증거일 뿐 "그래서 무엇이 좋아지나"에 답하지 못한다. 교수님은 편익과 구조를 본다. 방어 포인트를 수치 비교에 두면 심사가 엇나간다.
How: 초록, 결론, 그림의 무게를 편익에 둔다. 수치는 편익을 뒷받침하는 자리에 둔다.

편익 항목 예 (도메인에 맞게 바꾼다):
- 사람 개입 없이 실행되는가 (무개입 실행 시간)
- 대상 시스템을 수정하지 않고 적용되는가 (계측 불필요)
- 결함이 한 단위로 특정되어 디버깅 비용이 줄었는가
- 도메인 바인딩만 바꿔 다른 대상에 이식되는가
- 결과가 매번 같은가 (결정적 실행, 플레이키 없음)
- 테스트 케이스가 최소인데 커버리지는 최대인가

## 2. 프레임워크 그림 (필수)

- 프레임워크 전체를 한 장으로 보여주는 그림을 반드시 둔다. 예: 입력 → 단계들 → 계층(오케스트레이션, 어댑터, 실행 런타임) → 편익.
- 부품별 그림만 있고 전체 구조 그림이 없으면 교수님 기준에서 탈락이다. 과거 개정에서 전체 파이프라인 그림과 아키텍처 그림을 함께 없애 전체 구조 그림이 사라진 전례가 있다. 개정할 때마다 전체 구조 그림이 남아 있는지 먼저 확인한다.
- 결과 통계 그림(곡선 등)은 개수를 줄이고 표로 바꿔도 된다.

## 3. 연구실 핵심 메시지

- 교수님은 "최소의 테스트 케이스로 최대의 커버리지"를 연구실 이슈로 두셨다. 핵심 문제를 한 문장으로 정하고, 초록, 서론 문제 정의, 결론에 같은 말로 전면 배치한다.
- 본문 깊은 곳에만 있으면 심사자가 못 찾는다. 초록 앞부분과 서론 문제 정의에 노출한다. 2026-08-09 지시는 초록, 1장 문제 정의, 결론에 전면 배치하라는 것이었다.

## 4. 예상 질문 대비

심사에서 반복되는 질문을 미리 문서로 만든다.
- 왜 이 이론인가, 왜 이 기준인가 (선택 이유)
- 왜 최대 비용 경로인가 (목표와의 관계)
- 단위의 입도: 클릭인가 구매인가, 너무 세분화된 것 아닌가, 너무 추상적인 것 아닌가
- 확률의 근거: 누가 정했나, 실데이터는 있나
- 평가 지표의 목적: 이 지표가 원래 목적과 맞나
- 용어: 왜 이 이름인가, 소유자는 누구인가

각 질문에 대한 답은 본문에 이미 있어야 한다. 본문에 없으면 답변은 방어적이 된다.

## 5. 심사 답변서 작성

교수님 구술 답변을 답변서 문장으로 옮길 때의 원칙이다. 심사 내용 자체는 원고나 발표에 인용하지 않는다.

1. 취지 먼저: 교수님이 확정한 취지 문장을 답변 첫 줄에 둔다. 구술 취지가 빠지면 답변이 흩어진다.
2. 목적 재정의: 평가 목적이 원래 목적과 다르면 그 차이를 명시한다. 예: "원래 목적은 ○○ 예측이며, 본 평가는 학술적 관점에서 시도한 것이다."
3. 기준이 없는 목적을 정답 비교로 평가하지 않는다: 옳고 그름의 기준이 없는 목적(예: 과거 행위의 추정)에 정답 비교를 내세우면 공격당한다. 목적을 다시 정의하고 그 안에서 평가 항목을 정한다.
4. 항목별 한 문단: 심사자 항목마다 한 문단. 같은 취지의 질문이 여러 번 나오면 앞 답변을 참조한다("1-1 답변 참조").
5. 간결하게: 교수님은 "간단히 해서 빨리 하자"고 하셨다. 설명을 늘리지 않는다.
6. 분량 확인: 답변서가 쪽수 상한에 포함되는지 먼저 확인한다. 상한이 있으면 원고를 한 쪽 더 줄이는 식으로 맞춘다.
7. 원고 반영: 답변을 원고에 반영할 때는 답변에 해당하는 문장만 추가하거나 고친다. 교수님이 직접 고친 문장은 건드리지 않는다.
8. 답변 대상 자료 확인: 답변이 그림을 가리키면 그림 번호와 실제 그림이 일치하는지 확인한다. 한자 같은 세부는 원자료를 근거로 답한다.

Why: 교수님은 답변을 짧게, 취지 중심으로 쓰라고 하셨다. 답변이 길어지면 심사자의 질문이 다시 생긴다.
How: 답변서 초안을 쓰고 각 항목 첫 문장이 교수님 취지와 맞는지 확인한다.

## 6. AI 보조 사용 원칙

- AI로 만든 문장과 그림은 저자가 직접 읽고 고친다. 저자가 이해하지 못한 문장은 쓰지 않는다.
- 같은 요청을 반복해서 재생성하지 않는다. 중요한 부분만 골라 다시 만든다. 교수님은 많이 돌리지 말고 중요한 것만 돌리라고 하셨다.
- 자동 감지 점수를 낮추는 것이 목표가 아니다. 목표는 저자가 내용을 설명하고 책임질 수 있는 문장이다. (이 해석은 교수님 지시의 취지를 정리한 것이다.)
- 그림도 저자가 직접 검토하고 손질한다. 교수님은 그림을 사람이 그린 것처럼 다시 그리라고 하셨다.

## 7. 재현성

- 방법을 단계별로 쓴다. 다른 사람이 같은 순서로 구현할 수 있어야 한다.
- 블랙박스로 두지 않는다. 입력, 처리, 출력을 명시한다.
- 사용한 자동화 도구 이름과 버전을 명시한다. 부록에 재현성 체크리스트를 둔다.
- 데이터와 스크립트의 위치를 부록에 적는다(공개 가능한 범위에서).

## 8. 비공개 세부의 관리

- 교수님이 외부 공개를 제한한 세부(예: 특정 변환 절차의 상세)는 공개 원고, 발표, 키트에 넣지 않는다.
- 공개 전 "공개 범위"를 교수님께 확인한다. 확인 전에는 개요만 쓴다.
- 다른 연구자나 학생의 이름, 개인정보는 원고와 발표에서 제거한다.

## 9. stylechk 검수 (7항목)

검수 요청이 오면 아래 7항목을 순서대로 확인한다. 결과는 표로 낸다.

| # | 항목 | 확인 내용 |
|---|---|---|
| 1 | Voice & Person | "We propose ..." 사용, 1인칭 I 금지, 수동태와 능동태의 적절성 |
| 2 | 전환어 패턴 | "Further," 같은 세부 추가 전환, "Thus," 귀결, "In addition," 적절한 배치 |
| 3 | Gap 논증 | 선행 인정 → However → Thus 패턴 |
| 4 | 정의 4단계 | 각 개념이 정의 → 예시 → 논의 → 적용을 갖추었는가 |
| 5 | 인용 스타일 | 방법론 접점마다 자기 계보 인용, 연속 대괄호, 번호 주어 금지 |
| 6 | 수치 보고 | 기준선 비교, pp 표기, 정확과 샘플링 구분 |
| 7 | 절 시작 | "In this section, we present ..." 같은 개요 문장 |

출력 형식:

```
## 스타일 검수 결과 — <문서 버전>

| # | 항목 | 상태 | 위반 위치 | 수정 제안 |
|---|---|---|---|---|
| 1 | Voice | ✅/❌ | 절 번호, 줄 | 구체 제안 |
```

검수 실행 순서:
1. 기준 문서(이 스킬의 references)를 읽는다.
2. 대상 원고를 읽는다. 정본이 여러 개면 최신 버전을 쓴다.
3. `scripts/style_lint.py <원고>`를 돌려 기계적으로 잡히는 항목(번역체, 쉼표 인용, 수동태, 표 열 수 등)을 먼저 확인한다.
4. 7항목을 사람이 읽으며 확인한다.
5. 표로 보고하고, 수정은 새 버전 파일에 적용한다.

## 10. 검수 체크리스트 (요약)

- [ ] 편익이 초록, 결론, 그림에 드러나는가
- [ ] 프레임워크 전체 그림이 있는가
- [ ] 핵심 문제 문장이 초록, 서론, 결론에 같은 말로 있는가
- [ ] 예상 질문의 답이 본문에 있는가
- [ ] 심사 답변이 교수님 취지 문장으로 시작하는가
- [ ] 평가 목적이 원래 목적과 맞는가
- [ ] AI가 만든 문장을 저자가 직접 검토했는가
- [ ] 재현성 정보(단계, 도구, 버전)가 있는가
- [ ] 비공개 세부가 공개 원고에 들어가 있지 않은가
- [ ] stylechk 7항목을 모두 확인했는가
