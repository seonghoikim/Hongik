# 함정 목록 — 실제 사고에서 나온 규칙

각 항목은 **증상 → 원인 → 조치** 순서다. 근거는 프로젝트에서 실제로 겪은 사례다. 사례의 수치는 설명용 예시다.

## 1. "DPI를 300으로 저장하면 된다"

- **증상:** 메타데이터상 300dpi인데 인쇄에서 흐리다.
- **원인:** 조립기가 그림을 고정 폭으로 강제 리사이즈하므로 메타데이터는 결과에 영향이 없다. 실제 해상도는 픽셀 수 ÷ 인쇄 폭이다.
- **조치:** 픽셀 폭 ≥ 인쇄 폭(in) × 300으로 판정한다 (368pt → 1533.3px, 게이트는 올림한 1534px). `check_figure_print.py --png`.
- **근거:** 전수 실측에서 세 장이 176~190dpi로 미달했다.
- **추가 함정:** 원천 기록의 "1533px ≥ 300dpi"는 근사값이다. 1533px는 299.9dpi라서, 게이트를 1533으로 두면 통과하는 그림이 실제로는 미달이 된다. 키트 스크립트 두 개는 1534로 통일했다.

## 2. 캔버스가 넓어서 글자가 인쇄에서 작아진다

- **증상:** 화면에서는 큰 글자인데 인쇄 글자가 판독 불가다.
- **원인:** 실효 글자 = 글자 크기 × 인쇄 폭 ÷ 캔버스 폭. 캔버스가 넓으면 글자가 줄어든다.
- **조치:** 라벨을 줄이고, 주석 상자를 그림 밖으로 빼고, 캔버스를 좁힌다. 해상도를 올려도 해결되지 않는다.
- **근거:** 캔버스 1050pt에 13pt 글자 → 실효 4.6pt.

## 3. PDF 내장 이미지의 검은 배경 (SMask 누락)

SMask는 PDF 이미지의 투명도 마스크(알파 채널) 이미지다.

- **증상:** 원서나 참고 PDF에서 추출한 그림의 배경이 검고, 검은 글자·화살표·테두리가 사라진다.
- **원인:** 투명도 정보(SMask)를 무시하고 기본 추출을 하면, 투명 영역이 검은색으로 채워진다.
- **조치:** `extract_pdf_figures.py --images`는 SMask를 흰 배경에 합성한다. 추출 직후 `--render-pages`로 같은 페이지를 렌더해 나란히 비교한다.
- **근거:** 한 논문의 그림 다섯 장이 원 제출본부터 손상된 채로 여러 판에 걸쳐 잠복했다. 검게 나온 그림을 "원래 그런 것"으로 넘긴 것이 원인이었다. **검은 배경을 보면 추출을 의심한다.**

## 4. Graphviz 동일 랭크의 세로 순서는 선언 순서와 다르다

- **증상:** `rank=same`과 평행 간선 체인으로 순서를 정했는데 그림에서 노드가 다른 순서로 나온다. 한 예에서 AF-1이 3칸 밀려 AF-2, AF-3, AF-4, AF-1 순서가 되었다.
- **원인:** dot의 교차 최소화가 선언 순서를 재배열한다.
- **시도했으나 실패:** `weight=200`, `ordering=out`.
- **조치:** `verify_dot_order.py figure.dot --nodes "AF-1,AF-2,AF-3,AF-4"`로 좌표를 읽어 판정한다. 틀리면 체인 순서를 바꿔 가며 맞는 조합을 찾고, 찾은 방법과 근거를 `.dot` 주석으로 남긴다.
- **Why:** 눈으로 PNG를 열어 확인하면 매번 되돌아오게 되고, 놓치면 "정렬이 안 맞는다"는 지적을 받는다.

## 5. Read 도구가 PDF 페이지를 렌더하지 못한다 (스캔 논문)

- **증상:** 스캔본 PDF의 도식을 읽으라고 했는데 "렌더러가 없다"는 오류가 난다.
- **원인:** 이 환경에 PDF 렌더러(poppler)가 없다.
- **조치:** `extract_pdf_figures.py --render-pages <쪽> --dpi 190`으로 PNG를 만들고, PNG를 직접 연다. 확대가 필요하면 `--clip`과 `--dpi 520`을 쓴다.
- **서브에이전트에 판독을 맡기지 말 것:** 렌더러가 없는 상태에서 서브에이전트에 도식 판독을 맡기면, 본문 텍스트로 추론한 그럴듯한 판독이 돌아온다. 여러 에이전트가 같은 허위 내용을 일치하게 보고했고, 반증 단계를 붙여도 걸러지지 않았다. **여러 에이전트의 일치는 근거가 되지 않는다.** 판독은 PNG를 본인이 보고 기록한다. 서브에이전트에 맡길 때는 PNG 경로를 함께 넘긴다.
- **근거:** 원서 그림의 파선 개수, 자기 루프 여부, 라이프라인 집합에 대한 보고가 실제 PNG와 달랐다.

## 6. 고정좌표 도식에 글자만 키움

- **증상:** 글자를 두 배로 키웠더니 라벨이 노드와 겹치고, 캔버스 밖으로 잘린다.
- **원인:** 좌표, 간격, 캔버스가 글자 크기에 맞춰져 있지 않다.
- **조치:** 좌표·간격·캔버스를 함께 재배치한다. CSS flex/grid 기반이면 배율 확대가 통하는 경우가 많다.
- **근거:** 수치 검증은 통과했는데 눈으로는 겹쳐서 읽히지 않는 사례가 있었다. 검증 후 PNG를 반드시 눈으로 확인한다.

## 7. 자동 보정 스크립트가 원본 그림을 편집함

- **증상:** 발표용 글자 크기를 맞추려고 돌린 자동 보정이 논문용 원본 소스를 바꿨다.
- **원인:** 편집 대상 파일을 패턴으로 넓게 잡았다.
- **조치:** 보정 스크립트가 편집할 수 있는 대상을 발표용 소스(`*_pptsrc`)와 도식 폴더(`diagrams`)로만 제한한다. 논문용 원본은 읽기 전용으로 취급한다.

## 8. 렌더 배율을 빼고 계산함

- **증상:** 같은 그림이 어떤 스크립트에서는 통과하고 다른 스크립트에서는 미달로 나온다.
- **원인:** PNG 픽셀 폭을 CSS 폭으로 착각했다. 배율이 2배인 스크립트와 2.5배인 스크립트가 섞여 있었다.
- **조치:** 실효 크기 계산 전에 `PNG 픽셀 폭 / 배율 = CSS 폭`으로 되돌린다.

## 9. SVG를 Word에 직접 삽입 (판정 보류 — 기록이 상충함)

- **상충:** 한 기록은 "SVG 삽입은 Word에서 검증 완료"라고 한다. 다른 기록은 "Word에서 PDF로 변환하면 빈 상자로 나온 과거 사례가 있어 SVG 직접 삽입을 금지하고 PNG를 쓴다"고 한다.
- **조치:** 기본은 **PNG**를 삽입한다. SVG는 아래 절차를 통과한 Word 버전과 그림 종류에만 쓴다.
  1. 테스트 문서에 SVG 한 장을 삽입한다.
  2. 같은 문서를 PDF로 내보낸다.
  3. PDF에서 그림이 보이는지, 빈 상자가 아닌지 확인한다.
  4. 통과하면 같은 조건의 그림에만 SVG를 쓴다. 한 번이라도 실패하면 PNG로 돌아간다.

## 10. 특화 명칭의 아래첨자 표기

- **규칙:** 데이터의 키와 소스 ID는 평문으로 유지하고, **표시 계층에서만** 아래첨자와 이탤릭으로 바꾼다.
- **사고:** JavaScript로 표를 만드는 파일에서 키 문자열을 치환했더니 큰따옴표가 충돌해 구문이 깨졌다. 키를 바꾸지 말고, 표시 마크업(헤더 등)만 고친다.
- **표시 방법:**
  - Graphviz: `label=<<I>L</I><SUB>fas</SUB>>` (노드 ID는 그대로)
  - matplotlib: `$L_{fas}$`
  - SVG: `<tspan baseline-shift="sub">fas</tspan>`
  - Word: 텍스트를 쓸 때 런을 나눠 이탤릭 첫 글자와 아래첨자 나머지를 따로 쓴다. 완성된 문서에 Find 루프를 돌리는 사후 방식은 쪽 재배치가 폭발해 실패했다 (`word-insertion.md` §1).

## 11. 한글 폰트를 지정하지 않음

- **증상:** 그림의 한글이 네모나 다른 글꼴로 나온다.
- **조치:** Graphviz는 `fontname`, matplotlib는 `font.serif`/`font.sans-serif`, HTML은 `font-family`에 한글 폰트(맑은 고딕 등)를 명시한다.

## 12. GUI 도구나 AI 이미지로 본문 그림을 만듦

- **증상:** 그림을 고치라는 요청마다 처음부터 다시 그려야 한다. 같은 조건으로 재생성되지 않는다.
- **원인:** 소스가 없고 클라우드 결과가 바뀔 수 있다. AI 생성 그림은 설명 책임과 심사 정책 문제가 있다.
- **조치:** 본문은 코드 기반으로 만든다 (`tool-routing.md` §4). GUI 도구와 AI 이미지는 발표 초안이나 장식에만 쓴다.

## 13. 같은 이름의 원서 그림을 같은 단위로 대응시킴

- **증상:** 원서 그림의 "단위"를 우리 그림의 "단위"에 대응시켰더니 제목은 맞는데 정의가 다르다.
- **원인:** 원서의 단위가 입력부터 출력까지 왕복하는 구간인데, 우리 쪽은 한 메시지다.
- **조치:** 이름이 아니라 **정의(입력, 출력, 경계, 입도)**로 대응을 판정한다. `kim-mapping.md` §3.

## 14. 분기 확률의 합이 맞지 않음

- **증상:** 확률 트리에서 갈래 합이 1이 아니다.
- **조치:** 확률은 소스 데이터에서 생성하고, 생성 직후 갈림마다 합을 검사한다 (`figure-style.md` §3.2).

## 15. 옛 기록의 수치를 그대로 씀

- **증상:** 기록에 있던 "글자 19~26px이면 인쇄 6~8pt" 같은 값으로 새 그림을 설계했더니 인쇄에서 4~6pt가 됐다.
- **조치:** 기록 수치는 참고만 한다. 새 그림은 `print-quality.md` 공식으로 다시 계산한다. 기록끼리도 서로 맞지 않는 값이 있었다 (`print-quality.md` §4).

## 16. 확정본을 덮어씀

- **증상 (일반 원칙, 프로젝트 기록의 사고는 아님):** 교수님께 보낸 그림이 같은 이름으로 재생성되면, 어떤 버전을 보냈는지 알 수 없다.
- **조치:** 확정본과 제출본은 `_v2`, `_v3` 이름으로 보존한다. 초안 단계의 같은 이름 재생성만 허용한다 (`SKILL.md` §5). 전역 규칙의 "덮어쓰기 금지"와 맞추는 방식이다.

## 17. 공통 요소를 블록으로 떼어 그리고, 중복 노드를 자리마다 다시 그림

- **증상:** 매트릭스나 표에서 공통 BU(행동 단위)를 따로 모아 한 블록으로 그렸더니, 교수님이 그 구성을 지적했다. 같은 노드가 여러 자리에 그려져 공통 구간이 하나로 보이지 않았다.
- **원인:** 공통/특화를 분류 기준으로 나누어 그렸고, 실행 순서 대신 분류 순서로 배치했다.
- **조치:** 실행 순서대로 두고 공통 칸만 색이나 표식으로 구분한다. 같은 노드는 한 번만 그리고 여러 경로가 그 노드를 지나게 한다 (`figure-style.md` §3.9).
- **근거:** 프로젝트 피드백(2026-08-09)에서 통합 그래프 세 장과 공통성 매트릭스에 같은 지적이 나왔다.
