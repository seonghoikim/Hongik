# 셸 함정과 파일 규율

조판 작업 중 실제로 사고가 난 셸 함정과, 모든 작업에 적용하는 파일 규율을 모았다.
셸은 Git Bash(POSIX 문법)를 기준으로 하고, Windows 명령은 PowerShell 에서 쓴다.

---

## 1. 셸 함정

### 1-1. heredoc 의 백슬래시 손상 (가장 큰 사고)
- **증상**: `python - <<'PYEOF'` 안에 `"\\t"`, `"\\frac"`, `"\\to"` 같은 백슬래시 이스케이프를 넣으면, 파이썬이 그것을 해석해 **실제 탭·폼피드 문자**로 파일에 저장한다.
- 따옴표를 `'PYEOF'` 로 막아도 셸 확장만 막힐 뿐 파이썬 리터럴 해석은 그대로다.
- **실제 피해**: 원고 수식 `\to`, `\tag`, `\frac` 이 탭·폼피드가 되어 여러 판이 물려받았다. Word 판본에서 수식이 깨져 보였는데, 이미지처럼 보여 열흘 넘게 발견되지 않았다. 조판 스크립트의 `\textasciicircum`, `\triangle` 도 같은 방식으로 깨졌다.
- **방법**
  - 백슬래시가 든 코드를 고칠 때는 heredoc 대신 **Write 도구로 패치 파일을 만든 뒤 실행**한다.
  - 산출물에 제어문자 검사를 넣는다. `scripts/word_com_template.py` 의 `scan_control_chars()` 또는 `scripts/check_source.py` 를 쓴다.
  - 들여쓰기가 공백인 소스에 탭이 남아 있으면 전부 손상이다.

### 1-2. `>nul` 이 nul 파일을 만든다
- **증상**: Git Bash 에서 cmd 식 `>nul 2>&1` 을 쓰면 NUL 장치로 가지 않고 **`nul` 이라는 실제 파일**이 생긴다. git 은 이 Windows 예약 이름을 인덱싱하지 못해 `git add` 전체가 fatal 로 죽는다.
- **실제 피해**: 자동 백업 hook 이 13일간 조용히 실패해 미커밋 변경이 164건 쌓였다. hook 은 실패를 로그 파일에만 남기고 넘어가서 아무도 몰랐다.
- **방법**
  - bash 에서는 `>/dev/null`. PowerShell 에서는 `$null`. `>nul` 은 cmd.exe 를 거치는 경우에만 쓴다.
  - 프로젝트 스크립트가 `os.system("… >nul 2>&1")` 로 쓰는 것은 cmd 를 거치므로 안전하다. bash heredoc 안에서만 금지다.
  - nul 파일 삭제: `Remove-Item` 과 `del` 은 실패한다. 다음만 통한다:
    ```powershell
    [System.IO.File]::Delete('\?\C:\...\nul')
    ```
    확인은 `Test-Path` 가 아니라 `[System.IO.File]::Exists('\?\C:\...\nul')` 로 한다 (Test-Path 는 장치 이름과 혼동해 False 를 준다).
  - 백업이 멎은 의심이 들면 백업 hook 의 로그 파일 마지막 줄부터 본다.

### 1-3. 장시간 백그라운드 작업
- `| tail` 로 출력을 파이프하지 않는다. tail 은 EOF 까지 버퍼링하므로 진행 상황이 안 보이고, 멈춘 것을 몇 시간 동안 모르게 된다.
- `python -u` 로 실행해 로그를 스트리밍하고, 로그 파일을 직접 읽는다.
- 멈춤 판정은 메모리 사용량으로 하지 않는다. 프로세스의 CPU 시간을 두 번 재서 활동률로 판단한다 (`(Get-Process WINWORD).CPU` 를 간격을 두고 두 번).

### 1-4. taskkill 은 사용자 작업을 지운다
- `taskkill /f /im WINWORD.EXE` (또는 POWERPNT.EXE) 는 열려 있는 모든 창을 닫는다. 저장되지 않은 내용이 사라진다.
- 실행 전에 사용자가 Word 나 PowerPoint 를 열어 두었는지 확인하고, 허락을 받은 뒤 실행한다. 프로젝트 규칙이 "작업 전 taskkill" 을 요구하더라도, 열린 문서가 있으면 먼저 묻는다.

### 1-5. 경로와 인코딩
- 스크립트 경로는 **절대 경로**로 쓴다. 상대 경로는 작업 디렉터리에 따라 다른 파일을 가리킨다.
- 한글 출력을 쓰는 파이썬 스크립트는 첫머리에 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` 를 둔다.
- Windows 경로는 역슬래시 대신 슬래시(`C:/...`)로 쓰면 이스케이프 문제가 줄어든다. raw 문자열(`r"…"`)을 쓸 때도 끝의 역슬래시에 주의한다.

### 1-6. 단일 인스턴스
- Word COM 과 PowerPoint COM 은 한 번에 하나의 작업만 돌린다. 병렬 에이전트나 병렬 스크립트가 같은 Office 인스턴스를 건드리면 문서가 섞인다.

## 2. 파일 규율 (모든 작업에 적용)

1. **기존 파일을 덮어쓰지 않는다.** 산출물은 `_v{번호}` 또는 타임스탬프가 붙은 새 파일로 만든다. 예: `paper_v23.docx` 가 있으면 `paper_v24.docx`. 같은 이름이 있으면 `next_versioned_path()` 가 빈 이름을 고른다.
2. **재조판은 새 판 이름으로 한다.** 조판기의 기본 출력 이름도 새 판 이름이어야 한다. 옛 판 이름을 기본값으로 두면 실수로 덮어쓴다.
3. **원본은 읽기만 한다.** 공식 템플릿, 원고 소스, 게재본 PDF 는 조판 중에 고치지 않는다. 템플릿은 작업 사본으로 복사해서 쓴다.
4. **시험 조판은 scratch 폴더에서 한다.** 확정본만 프로젝트 폴더에 낸다. 시험 PDF 를 프로젝트 폴더에 쌓아 두면 어느 것이 확정본인지 헷갈린다.
5. **검수 결과도 버전을 나눈다.** 렌더 PNG 폴더, 쪽별 빈칸 측정 결과, 스팬 실측 결과를 판마다 따로 둔다.
6. **끝나면 변경 사항을 체크리스트로 보고한다.** 무엇을 새로 만들었고, 무엇을 검사했고, 무엇이 남았는지를 적는다.
7. **임시 파일은 scratch 폴더에 둔다.** 프로젝트 폴더를 임시 파일로 어지럽히지 않는다.
