# 작업 규율 (파일, 피드백 처리, 산출물 동기화, 소스 표기)

## 1. 파일 규율

- 기존 파일을 덮어쓰지 않는다. 수정본은 `_v{번호}` 접미사나 타임스탬프가 붙은 새 파일로 저장한다. 예: `paper_v12.md` → `paper_v13.md`.
- 정본(기준본)을 하나 정해 두고, 정본 안내 문서(버전 이력)에 버전, 날짜, 변경 요지, 분량을 기록한다.
- 커밋 메시지를 쓰는 저장소라면 한글 동사형으로 시작한다. 예: "추가: ...", "수정: ...", "삭제: ...", "개선: ...".
- 자동 백업 훅이 있으면 수동 push는 필요 없다. 백업이 실패하면 원인을 먼저 찾는다. 예: 셸 리다이렉션 실수로 생긴 Windows 예약 이름 파일(nul)이 git add를 실패시켜 백업이 멈춘 사례가 있었다.

Why: 교수님 피드백은 이전 버전과 비교해서 확인된다. 덮어쓰면 승인받은 문장을 되돌릴 수 없다.
How: 저장 전에 대상 파일명이 이미 있는지 확인하고, 있으면 다음 번호를 쓴다.

## 2. 피드백 처리 절차

1. 원본 확보: 음성 파일(또는 메모, 손글씨 사진)을 원본 폴더에 보관한다. 원본을 지우지 않는다.
2. 전사: 음성 인식 도구로 전사하고 모델 크기와 조건(CPU/GPU, 청크 수)을 기록한다. 인식 품질이 낮으면 원음 타임스탬프와 메모로 대조한다.
3. 발췌: 원문 인용은 타임스탬프와 함께 짧게 쓴다. 긴 전문은 별도 파일로 둔다.
4. 해석: 문맥으로 보정한 해석을 쓴다. 보정이 불확실한 곳은 ⚠️로 표시한다.
5. 체크리스트: P1(마감 전 필수), P2(본문 보강), P3(여유가 되면)으로 나눈다. 항목마다 ☐/☑ 상태, 반영 위치(절 번호)를 쓴다.
6. 판단 필요 표: 교수님이나 저자가 정해야 할 쟁점을 표로 쓴다. 상태(해소, 미해소)를 함께 쓴다.
7. 승인 목록: 교수님이 "잘했다"고 한 항목을 따로 적는다. 이 항목은 변경하지 않는다.
8. 반영과 검증: 반영 후 해당 항목을 ☑로 바꾸고, 린트와 수치 대조를 돌린다.

교수님 지시 한 건은 체크리스트 항목 한 개로 옮긴다. 여러 지시를 한 항목에 묶지 않는다.

원천 확인 원칙: 스캔한 PDF나 사진 도식은 텍스트 추출이나 요약에 기대지 말고, 페이지를 이미지(PNG)로 뽑아 직접 본다. 하위 에이전트에 판독을 맡겼을 때 도식을 보지 못하고 본문에서 내용을 지어낸 사례가 있었다. 판독이 불가하면 "판독 불가"라고 보고하게 한다.

## 3. 교수님 직접 교정 보존

- 교수님이 직접 고친 원고가 있으면 직전본과 교정본을 비교한다(diff).
- 교정 패턴(문형, 복합어, 주어, 철자)을 뽑아 새 원고에 적용한다.
- 교정으로 바뀐 문장은 건드리지 않는다. 새 수정이 교정본과 충돌하면 교정본을 우선한다.

## 4. 산출물 동기화

한 논문이 여러 산출물(국문판, 영문판, 발표 자료, 그림 전용 자료)로 나갈 때 다음을 지킨다.
- 기준본을 하나 정한다. 나머지 산출물은 기준본에서 동기화한다.
- 동기화할 때 기준 버전과 날짜를 각 산출물의 이력에 쓴다.
- 용어, 수치, 그림 번호는 기준본과 대조한다.
- 한 산출물에서 고친 내용(예: 새 용어)은 다른 산출물에도 같은 날 반영한다. 반영이 늦으면 용어가 두 개가 된다.

학위논문과 저널 논문을 같은 연구에서 나눌 때:
- 용어와 수치의 정본을 하나 둔다.
- 논문별 차이(범위, 분량, 제목, 강조점)를 표로 관리한다.

## 5. 소스 표기와 표시 표기

원고 소스(마크다운, 데이터 파일, 코드)와 최종 조판(문서, 슬라이드)의 표기를 분리한다.

- 소스에는 안전한 평문 ID를 쓴다. 예: `Lfas`.
- 아래첨자, 이탤릭, 수식 같은 표시는 조판이나 렌더링 단계에서만 적용한다.
- 데이터 식별자(JSON 키, 코드의 ID)는 치환하지 않는다. 표시 텍스트만 바꾼다. 식별자를 바꾸면 데이터와 코드가 깨진다. 과거에 JS 문자열 리터럴을 치환하다 구문이 깨진 사고가 있었다.
- 표 셀 안에는 리터럴 파이프 `|`를 쓰지 않는다. 절댓값처럼 수식에 `|`가 필요하면 `\mid`로 쓰고, `\mid`를 `|`로 바꾸는 일은 렌더 단계에서 한다. 리터럴 `|`가 있으면 셀이 쪼개져 빈 열이 생긴다.
- 표를 고친 뒤에는 행마다 열 수가 같은지 검사한다. Git Bash에서는 `awk -F'|' '{print NF-2}' 파일.md`로 행별 열 수를 볼 수 있다. 린트 스크립트도 같은 검사를 한다.

## 6. 수식이 있는 원고 편집

- 수식이나 백슬래시가 많은 원고는 셸 heredoc(`cat << EOF`)으로 쓰지 않는다. 셸이 백슬래시를 해석해 수식이 깨진다. 과거에 원고 수식과 조판 스크립트가 깨진 사고가 있었다.
- 편집 도구(파일 쓰기, 부분 교체)로 파일을 직접 다룬다.
- 패치 스크립트는 파일로 저장해서 실행한다.

## 7. 전역 치환 후 검증

1. 치환 전 대상 검색 결과 수를 센다.
2. 치환한다.
3. 옛 용어와 옛 표기를 다시 검색해 0건인지 확인한다.
4. 수치는 원천 파일과 대조한다.
5. 린트 스크립트를 돌린다.
6. 문서별 수정량 표를 남긴다.

## 8. 공개 범위와 개인정보

- 교수님이 외부 공개를 제한한 세부는 공개 원고, 발표, 공개 키트에 넣지 않는다.
- 다른 연구자나 학생의 실명, 개인 메일, 개인 PC 경로, 계정 이름은 공개 문서에 넣지 않는다. 자리표시(예: `<저자>`, `<HOME>`)로 바꾼다.
- 심사 내용과 투고 시스템의 세부는 공개 문서에 옮기지 않는다.
- 미공개 원고의 긴 문장은 공개 문서에 인용하지 않는다.

## 9. 저작권과 인용

- 타인 논문의 문장을 복제하지 않는다. 문장 틀(구조)만 참고하고 내용은 새로 쓴다.
- 자기 논문의 문장은 자기 원고 안에서 재사용할 수 있다.
- 그림과 표를 가져오면 출처를 밝힌다.
- 인용은 짧게 하고, 요약은 원문과 충분히 다르게 쓴다.

## 10. 재제출과 심사 대응 문서 관리

- 재제출에서는 원고 버전과 답변서 버전을 분리해 관리한다.
- 반영 내역표를 만든다: 심사 지적(요지), 답변, 원고 위치(절 번호), 반영 상태.
- 심사 지적 원문은 답변서 작업 메모에만 두고, 원고에는 옮기지 않는다.
- 답변서 분량은 원고 분량과 별도로 확인한다.

## 11. 완료 보고 형식

작업 완료 시 변경 사항을 체크리스트로 보고한다. 형식은 SKILL.md §5를 따른다.

보고에 들어갈 것:
- 변경한 파일(새 버전 파일명)과 바뀐 절
- 체크리스트 항목별 상태
- 판단 필요 항목과 상태
- 린트 결과(error, warn, info 개수)
- 수치 대조 결과와 원천 파일 위치
- 아직 하지 않은 것과 이유

## 12. 작업 전 점검 목록

- [ ] 정본 파일과 버전 이력을 확인했는가
- [ ] 최근 피드백 체크리스트와 판단 필요 항목을 읽었는가
- [ ] 저장할 파일명이 기존 파일과 겹치지 않는가
- [ ] 수식이 있다면 heredoc을 쓰지 않았는가
- [ ] 표를 고쳤다면 열 수를 검사했는가
- [ ] 전역 치환 전에 검색 결과 수를 세었는가
- [ ] 공개 범위 제한 항목이 공개 문서에 들어가지 않았는가
- [ ] 스캔 도식이나 사진 원천을 텍스트 요약이 아니라 이미지로 직접 확인했는가
