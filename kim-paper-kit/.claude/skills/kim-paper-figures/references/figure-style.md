# 그림 양식 — 지도교수 컨펌 기준

이 문서는 그림 한 장을 설계하고 검토할 때 쓴다. 인쇄 수치는 `print-quality.md`, 원서 대응은 `kim-mapping.md`를 본다. 아래 사례의 날짜와 수치는 프로젝트 기록이며, 규칙은 다른 주제에도 그대로 적용한다.

## 1. 판정 기준 한 줄

- 그림은 정보량이 아니라 **30초 안에 한 문장으로 읽히는가**로 판정한다.
- 교수님은 그림만으로 논문의 흐름이 잡히기를 원한다. 그림이 본문보다 먼저 읽힌다고 보고 설계한다.
- **Why:** 상자 안에 문장이 6~10줄 들어가고 글자가 4pt 수준인 그림은 지적을 받았다. 반대로 계층 표와 확률 트리처럼 구조가 한눈에 보이는 그림은 좋은 평가를 받았다.
- **How:** 그림을 그리기 전에 메시지 한 문장을 적는다. 그 문장과 무관한 요소는 빼거나 다른 그림으로 옮긴다.
- **구도는 저자가 정한다.** 교수님은 "내 아이디어에 맞는 샘플 그림"으로 그리는 방식을 확인하셨다. 구도(무엇을 어디에 둘지)는 손스케치로 정하고, 그림은 코드로 그린다.

## 2. 시각 규칙 (도식·다이어그램·표)

| 요소 | 규칙 | 비고 |
|------|------|------|
| 바탕·선·글자 | 흰 바탕, 검정 | 기본 색은 검정 하나 |
| 강조 | **빨강 하나** (프로젝트 값 `#B03A2E`) | 핵심 경로, 제안 방식, 선택된 결과에만 쓴다 |
| 비강조 | **회색 두 단계** (예시 값: 연회색 `#B9B9B9`, 중간회색 `#666666`) | 회색 단계는 두 개로 제한한다. 값은 예시이며 프로젝트 값과 다를 수 있다 |
| 색 의미 | 같은 색은 모든 그림에서 같은 뜻 | 예: 제안 방식은 항상 빨강 |
| 선 굵기 | 다이어그램 테두리 1~2px, 강조 선 4~5px (프로젝트 기록) | 플롯 선은 1.6pt (`paper_style.py` 기본). 흑백 인쇄에서도 구분되게 굵기를 함께 쓴다 |
| 글꼴 | 본문과 같은 세리프 (라틴 Times New Roman), 한글은 맑은 고딕 폴백 | 본문 폰트와 맞춘다 |
| 라벨 | 명사구, 한 상자 3줄 이내 | 완성 문장은 본문으로 옮긴다 |
| 크기 | 실효 8pt 이상 | `print-quality.md` 공식으로 확인 |

**데이터 플롯은 예외다.** 막대·선·산점도·히트맵은 색각 이상자도 구분하는 Okabe-Ito 8색 팔레트를 쓴다 (`scripts/paper_style.py`). 도식(트리·매트릭스·계층 표)은 위의 검정·빨강·회색 규칙을 쓴다. 두 규칙을 한 그림에 섞지 않는다.

- **Why:** 교수님 양식은 빨강 하나와 회색 단계로 강조를 주는 방식이다. 플롯을 여러 색으로 칠하면 도식의 강조가 사라진다.

## 3. 구조 문법 (우선 검토할 형식)

### 3.1 계층 세분화 표 (실행 순번 색칠)

- **용도:** 항목이 수백 개인 대상(메소드, 상태, 상호작용)을 전부 그리지 않고 계층별 덩어리로 보여 준다. 무엇을 실행했는지 색칠로 표시한다.
- **구성:** 열 = 계층 레벨 (예: 유스케이스 → 시나리오 → 상태 → 오브젝트 → 메소드). 칸 = 항목. 실행한 칸에 실행 순번을 적고 빨강(강조 색)으로 칠한다. 미실행 칸은 외곽만 남겨 구분한다.
- **계층 수:** 프로젝트 사례는 5단 안팎이었다.
- **3층 예:** "단위 → 중간 덩어리 → 시나리오"처럼 세 층을 같은 표 문법으로 그린다. 프로젝트에서는 중간 덩어리인 DU(Dialogue Unit, 입력과 출력 사이의 왕복 구간)를 이 방식으로 설명할 그림을 계획했다.
- **Why:** 교수님 피드백에서, 항목을 전부 그리는 것보다 계층 단위로 묶어 보여 주는 편이 비용과 범위를 설명하기 쉽다는 지시가 있었다. 약 179개 항목을 전부 그리는 대신 계층 색칠 표로 바꾸었다.
- **도구:** HTML 표(CSS grid) + `render_html_figure.py`.

### 3.2 확률 트리 (좌에서 우로)

- **구성:** 왼쪽에서 오른쪽으로 진행한다. 갈림마다 갈래 확률을 표시한다. 한 갈림의 갈래 확률 합은 1이다.
- **검증:** 확률 값은 소스 데이터에서 생성한다. 손으로 쓰지 않는다. 갈림마다 합을 계산하는 검사를 소스 단계에 넣는다.
- **Why:** 교수님은 한 갈림의 확률 합이 100%가 되도록 정규화해서 보여 줄 것을 요청했다. 정규화 방법(프로젝트 예: 볼츠만 정규화)은 이론 장표를 따로 두어 설명하고, 그림에는 결과 확률만 둔다.
- **도구:** Graphviz (`rankdir=LR`) 또는 HTML/CSS.

### 3.3 원서 문법 재작 (대응 그림)

- 원서(지도교수의 학위논문 등)에 같은 역할의 그림이 있으면, 새 문법을 만들지 말고 원서 문법을 용어만 바꿔 그대로 쓴다.
- 자주 쓰는 원서 문법 요소와 재작 규칙은 `kim-mapping.md` §4에 정리했다.

### 3.4 대비 그림 (기존 방식과 제안 방식)

- 같은 입력에 대해 두 방법의 결과를 나란히 둔다. (a)(b) 패널 또는 좌우 배치.
- 제안 쪽의 선택 결과에만 빨강을 쓴다.
- **예 (프로젝트 사례):** 최적화 알고리즘은 경로 하나만 고르고, 비최적화(전수 보존)는 모든 잎을 남긴다. 한 장에서 "무엇이 남는가"가 바로 보이게 그린다.
- **기각 예:** 정의의 경계가 애매하면 기각 예를 나란히 둔다. 프로젝트에서는 "클릭은 단위가 아니고 구매는 단위다"를 대비 그림으로 계획했다.

### 3.5 프레임워크 전체를 한 장으로

- 입력 → 주요 단계 → 출력 → 편익 순서로 전체 구조를 한 장에 둔다.
- **Why:** 교수님 기준은 부품별 그림만 있고 전체 구조 그림이 없으면 통과하지 못한다. 판을 고치면서 전체 구조 그림을 지운 전례가 있었으므로, 판을 바꿀 때 전체 그림이 남아 있는지 항상 확인한다.

### 3.6 수치 그래프는 핵심 비교만

- 교수님의 잣대는 수치의 우수성이 아니었다 (프로젝트의 세 번째 논문 기준, 2026-09-18 확인). 자동화가 주는 편익과 논리 구성이 그림으로 읽히는지를 본다.
- 결과 플롯은 개수를 줄이고 핵심 비교만 남긴다. 나머지는 표로 내린다.
- 편익을 그림에 드러내는 예: 실행 시간, 대상 시스템 무수정, 결함의 위치 특정, 결정적 실행.

### 3.7 유스케이스 개요도 (시스템 경계와 액터)

- **구성:** 시스템 경계 상자 안에 유스케이스(타원), 밖에 액터. 프로젝트에서는 몰 전체를 시스템 경계로, 매장 하나를 유스케이스로 놓았다.
- **액터:** 사용자(고객)와 테스트 에이전트를 함께 둔다. 교수님은 에이전트도 액터로 보이기를 요청했다.
- **공통 요소:** "공통 흐름"이라는 라벨은 뜻이 불분명하다는 지적을 받았다. 대신 **각 유스케이스 내부에 공통 요소가 있다**는 구도로 그리고, 포함(include)류 관계 화살표로 나타낸다.
- **내부 그래프:** 유스케이스 하나의 내부에 시나리오 그래프가 있다는 관계가 보이게 한다 (상위 정의와 내부 그래프의 관계).
- **도구:** Graphviz (`cluster`, 이미지 액터, `dir=back`). 프로젝트 논문 그림 9가 이 방식이다.

### 3.8 흐름도 대신 스텝 플로우

- 교수님은 다른 학생을 지도하면서 "플로우차트 말고 스텝 플로우"로 그리라고 하셨다. 판단 분기 중심의 플로우차트 대신, 단계 번호가 순서대로 읽히는 그림을 원칙으로 삼는다. 이 키트는 그 발언을 그림 작성 원칙으로 채택했다.
- 단계마다 번호와 짧은 명사구 라벨을 붙인다. 순서가 의미를 가지면 `verify_dot_order.py`로 확인한다.

### 3.9 정렬과 병합 (공통 요소 표시)

- **공통 요소는 색으로 구분하고 블록으로 떼지 않는다.** 공통 BU(Behavior Unit, 프로젝트가 정의한 행동 단위)를 따로 모아 두는 방식은 하지 말고, 실행 순서대로 두고 공통 칸만 색이나 표식으로 표시하라는 지시가 있었다.
- **열·행 순서는 실행(그래프 위상) 순서다.** 알파벳이나 ID 순서로 나열하지 않는다.
- **중복 노드는 병합한다.** 같은 노드가 여러 자리에 그려지면 하나로 합쳐 공통 구간이 한 줄로 보이게 한다. 여러 경로가 한 노드로 모이는 구조(예: 다이얼로그 맵의 수렴)는 수렴 노드를 하나로 뭉친다.
- **시나리오는 우선순위 번호로 나열한다.** 표의 시나리오 행을 1, 2, … 순번으로 제시하는 판을 검토했다.
- **Why:** 교수님은 같은 BU가 여러 자리에 중복 배치된 곳을 찾아 병합하라고 지시했다. 그래야 공통 구간이 시각적으로 하나로 보인다.

## 4. 그림 한 장 설계 절차

1. **메시지 한 문장을 적는다.** 예: "이 기법은 경로를 버리지 않는다."
2. **문법을 고른다.** 원서 대응이 있으면 원서 문법 (3.3). 없으면 3.1~3.8 중 택1.
3. **요소를 뺀다.** 메시지와 무관한 상자, 주석, 색은 제거하고 캡션이나 본문으로 옮긴다.
4. **라벨을 줄인다.** 명사구, 3줄 이내.
5. **흑백 미리보기.** 빨강 강조가 한 곳만 남는지, 회색 단계가 두 개인지 본다.
6. **30초 테스트.** 그림을 3초 보여 준 뒤 메시지를 말해 본다. 말하지 못하면 3단계부터 다시 한다.

## 5. 캡션과 본문

- **캡션은 제목만.** 한 문장, 번호와 끝 마침표. 패널 설명, 결론, 수치 해석은 본문 문단에 쓴다.
- **Why:** 캡션에 설명을 길게 쓰면 그림이 읽히지 않고, 설명이 본문과 중복된다.
- **접두와 언어는 투고 규정이 우선.** 프로젝트에서 확인한 차이:

| 양식 (프로젝트 확인) | 캡션 접두 | 언어 | 위치 | 본문 참조 |
|----------------------|----------|------|------|----------|
| IJIBC 규격 (프로젝트 기준, 국제 저널) | `Figure N. 설명.` | 영문 | 그림 아래 | Figure N |
| TKIPS 논문지 (정보처리학회 논문지, 2단) | `Fig. N.` (표는 `Table N.` 위) | 영문 | 그림 아래 | Fig. n |
| TIIS (KSII 국제 저널) | `Fig. N.` (접두 파랑·볼드 10pt) | 영문 | 그림 아래 | Fig. n 파랑·볼드 |
| 정보처리학회지 (1단, 한글판) | `(그림 N)` | 한글 | 그림 아래 | 규정 확인 |

- **영문·국문 이중판:** 프로젝트에서는 영문 그림을 별도 폴더(`figs_en/`)에 두었다. 라벨은 소스에서 언어별 사전으로 분리하고, 소스는 하나로 유지하는 방식을 권장한다. 파일명에 `_ko`, `_en` 접미사를 붙이는 방식은 이 키트의 제안이며 프로젝트에서 확정된 규칙은 아니다.

## 6. 교수님 피드백을 그림 작업으로 바꾸기

1. **음성은 자동 전사하고, 인식이 낮은 구간은 손글씨 메모와 사진으로 대조해 해석한다.** 원문과 해석을 칸으로 나눠 둔다.
2. **항목을 분류한다.** P1 그림 신설 / P1 형식 / P2 구조 / P3 용어 등.
3. **항목마다 원문 시각(타임스탬프)과 해석 한 줄을 붙인다.**
4. **손스케치는 번호를 매겨 사진으로 보관한다.** 스케치마다 "대응 그림 유형"을 적는다.
5. **그림 항목은 추적표로 관리한다.** 프로젝트는 피드백을 P1~P3 체크리스트로, 원서 대응을 대응표(상태·격차·조치·우선순위)로 관리했다. 그림 추적표도 같은 방식으로 둔다. 열 예: 그림 번호, 유형, 도구, 소스 파일, 상태.

- **Why:** 피드백 항목이 본문, 그림, 발표 자료에 흩어지면 빠짐이 생긴다. 추적표 하나로 모은다.

**요청 그림 계열 사례 (프로젝트 2026-08-02 피드백).** 교수님이 요청한 그림은 다음 계열이었다. 같은 대상을 다른 문법으로 나눠 보여 주는 방식이 많았다.

- 몰 유스케이스 개요도 (매장 = 유스케이스, 몰 = 시스템 경계) → 3.7
- 시나리오별 개별 경로 그림 (경로 하나씩, 순서 있는 목록 형식)
- 확률값 3패널 (기본 구조 / 다이얼로그 맵 / 확률 매트릭스)
- 시나리오별 행위 매핑 한눈 표 (에이전트가 할 수 있는 행위)
- 추상 → 브레이크다운 줌인 구조도 (유스케이스 → 상세 테이블 체인)
- 커버리지 덩어리 그래프 (경로가 겹치는 영역과 중복 구간)
- 가중 테스트 트리 (그래프를 트리로 바꾸고 가중치 표시)

**예 (프로젝트):** 시스템 경계와 유스케이스를 그린 스케치는 "몰 유스케이스 개요도 → 시나리오별 인터랙션 → 가중 트리"의 3단 그림 계열로 번역했다.

## 7. 자주 나오는 지적 (요약)

- 글이 많은 상자, 자잘한 글자 → 라벨을 명사구로 줄인다.
- 색이 여러 개 → 빨강 하나, 회색 두 단계로 되돌린다.
- 캡션에 설명이 길다 → 제목만 남기고 본문으로 옮긴다.
- 분기 확률의 합이 맞지 않는다 → 소스에서 생성하고 합을 검사한다.
- 부품 그림만 있다 → 프레임워크 전체 그림을 추가한다.
- 공통 구간이 블록으로 떨어져 보인다 → 실행 순서대로 두고 색으로 구분한다 (3.9).
- 같은 노드가 여러 번 그려졌다 → 병합한다 (3.9).
- 라벨 "공통 흐름"처럼 뜻이 모호하다 → 관계 화살표로 바꾼다 (3.7).
- 그림 이름은 같은데 단위가 다르다 → `kim-mapping.md`의 재분류 기준으로 다시 본다.
